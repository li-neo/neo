# NEO：IM + OpenClaw + Skill + CLI 的自我迭代架构范式（中文方案）

## 1. 一句话摘要

通过 IM 触发云端 OpenClaw，OpenClaw 在宿主机上自动安装/授权 `neo` CLI，并调用 `neo-site-manager` Skill 执行站点运维与内容 CRUD，从而实现“可远程、可审计、可自我迭代”的网站自动化运营闭环。

## 2. 为什么这是“先进架构”

这套架构的先进之处不是“又加了一个机器人”，而是把网站的演进能力标准化成三层可组合能力：

- **标准输入层（IM）**：自然语言任务入口，适配多种渠道（Feishu 等）。
- **标准执行层（OpenClaw + Skill）**：任务规划 + 可控工具调用，具备可插拔技能体系。
- **标准操作面（NEO CLI）**：把“改网站”收敛成一致的、可测试的、可复用的命令接口（而不是 UI 点点点或散落脚本）。

最终形成一个关键属性：**可自我迭代（Self-Improving）**  
原因是：从 IM 到 CLI 的全链路可脚本化、可复现、可记录，迭代成本低，反馈速度快。

## 3. 端到端链路（你当前项目的实际闭环）

### 3.1 业务闭环

1. 你在 IM 中提出需求（例如“查看所有留言 / 发布一篇草稿 / 导入文章”）
2. OpenClaw 在云端宿主机收到消息
3. OpenClaw 选择 `neo-site-manager` Skill
4. Skill 在宿主机执行 `neo` CLI（不是让用户手动执行）
5. `neo` 调用 NEO API 完成操作
6. OpenClaw 将结果回传到 IM

### 3.2 授权闭环（跨机器、无浏览器也可用）

云端宿主机没有浏览器时，仍然可以安全授权：

1. 宿主机发起 `bootstrap` 授权（`neo openclaw bootstrap`）
2. 宿主机把**批准链接**回传给你（IM 里只发链接）
3. 你在任意浏览器打开链接，GitHub 登录并批准
4. 宿主机后台自动领取 `neo_pat_...` 并落盘保存
5. 后续所有 IM 指令都能直接自动执行，无需重复授权

## 5. 关键设计原则（通用范式）

这套方案可以抽象成一个通用范式，适用于任何“需要远程自动化运营/运维”的系统：

### 5.1 三层分离：入口 / 执行 / 操作面

- **入口层（Input）**：IM / Chat / API
- **执行层（Orchestration）**：Agent + Skill（可插拔）
- **操作面（Control Plane）**：统一 CLI（可测试、可审计、可复用）

> 通用原则：让 AI 只负责“决定做什么”，让 CLI 负责“怎么可靠地做”。

### 5.2 授权必须“远程友好”

远端机器没有浏览器是常态，而不是例外。  
因此授权应该满足：

- **不需要把 JWT 手工复制到远端**
- **只需要浏览器批准一次**
- **远端自动领取、自动落盘**
- **token 可撤销、可过期、可审计**

### 5.3 Fail-fast 与确定性输出

自动化最怕“卡住”。因此必须：

- 未认证时立即返回明确可执行的下一步（批准链接）
- 不再让 Agent 盲目重试导致超时
- 输出必须结构化（JSON / 固定字段）以便 OpenClaw 稳定解析与转述

### 5.4 “自我迭代”来自闭环而不是魔法

所谓自我迭代，本质是：

- IM 反馈快
- CLI 行为可复现
- 操作可观测、可回放、可归因
- 迭代不依赖人工点 UI

## 6. 你项目里已经具备的能力点（可对外宣传的亮点）

- **统一控制平面**：所有站点管理最终收敛到 `neo` CLI
- **可插拔执行器**：OpenClaw Skill 体系让能力可扩展
- **跨机器安全授权**：bootstrap 授权避免 JWT 手工分发
- **可演进 API**：`/api/v1` 保兼容，`/api/v2` 可逐步演进
- **可运维**：system lifecycle、health、logs 等操作一体化
- **可自动化运营**：内容 CRUD + 导入（URL / 文件）可脚本化

## 7. 推荐的“顶级思路”模板（可复制到其他项目）

你可以把这套方案概括成一个更通用的“AI 运营/运维系统范式”：

1. **把产品的所有可变更点提炼成 CLI**（控制平面）
2. **让 Agent 只做规划**，Skill 只做执行（分层）
3. **把授权做成浏览器批准式**，远端自动领取（远程友好）
4. **把所有执行结果结构化返回**，避免卡住与歧义（确定性）
5. **通过 IM 将反馈回路缩短到分钟级**（自我迭代）

## 8. 落地建议（下一步可增强项）

- Token 增加 scope（只读/内容写入/运维），减少爆炸半径
- 引入审计日志（谁/何时/通过哪个 IM 会话/改了什么）
- 引入 dry-run（写操作先生成 diff/变更单，再执行）
- 更强的“可观测性”：把每次 CLI 调用的耗时/错误码统一上报
